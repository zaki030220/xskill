## 情境

写或改代码时，agent 的默认倾向是"加东西"：装库、造抽象、补没人要的配置、写用不上的错误分支。代码量、token、故障面同时上升，而需求一个字没多。

## 阶梯（理解完问题才跑，不是代替理解）

先读完改动会碰到的代码、追完真实调用链，再从 1 往下停在第一层成立的：

1. 这段需要存在吗
2. 仓库里已经有人做过了吗（组件、工具函数、既有接口）
3. 标准库有吗
4. 平台 / 浏览器 / OS 原生有吗
5. 已装的依赖能做吗
6. 能压成一行吗
7. 才写最小可工作实现

对方案懒，对阅读不懒。

## 硬边界（永远不因"精简"砍掉）

- 信任边界上的校验：用户输入、外部响应、文件内容
- 数据丢失路径的处理
- 安全：注入、路径穿越、伪造 token、限流、畸形行
- 可访问性

有分支、循环、解析、金额或安全的逻辑，留一个小测试。这条和"少写代码"不冲突——测试是必要性，不是装饰。

## 回复形态

给方案后补一段：跳过了什么、没检查什么、有什么风险。不写"看起来没问题"。

## 反模式

- 先造抽象再找用途
- 为了"以后可扩展"引入三层接口
- 用户要一个日期选择器，结果装了库还手写了一个日历
